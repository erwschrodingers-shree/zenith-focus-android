# Contributing to Zenith

Thank you for your interest in contributing to Zenith!

## Code Style

We follow standard Kotlin conventions:

- Use 4 spaces for indentation
- Use Kotlin naming conventions (camelCase for variables/functions, PascalCase for classes)
- Write descriptive variable names
- Add KDoc comments for public functions

## Branch Naming

- `feature/description` - New features
- `bugfix/description` - Bug fixes
- `refactor/description` - Code refactoring
- `docs/description` - Documentation updates

## Commit Messages

Use descriptive commit messages:

```
[FEATURE] Add audio loop player with volume control
[BUGFIX] Fix timer not persisting after app restart
[DOCS] Update permission setup guide
```

## Pull Request Process

1. Fork the repository
2. Create a feature branch (`git checkout -b feature/your-feature`)
3. Commit changes (`git commit -m "[FEATURE] Description"`)
4. Push to branch (`git push origin feature/your-feature`)
5. Open a Pull Request with description of changes
6. Ensure CI passes (Gradle build, linting)
7. Request review from maintainers
8. Address feedback and squash commits if needed
9. Merge after approval

## Areas for Contribution

- **Bug Fixes**: Report issues or submit fixes
- **Features**: Suggest new features (check issues first)
- **Documentation**: Improve README, code comments, guides
- **Testing**: Add unit/instrumented tests
- **Translations**: Add i18n support for new languages
- **UI/UX**: Design improvements, accessibility

---

**Questions?** Open an issue or contact the maintainers.
